## 2. 렌더 파이프라인 문제 해결 과정

### 2-1. 증상

작업은 `Completed`로 표시되는데 결과물이 하나도 생성되지 않았다.

```
WARNING | Aborted by user: received abort signal
Error: RuntimeError: [mtoa] Failed batch render
```

Task 소요 시간 수 초, 평균 CPU 사용률 1%. 즉 렌더를 시작하지도 못하고 종료된 상태였다.

### 2-2. 원인 추적

원인을 세 단계에 걸쳐 좁혔다.

**① 라이선스 문제로 추정 → 부분적으로만 맞음**

Maya 2025로 제출하면 `[clm.v1] generic license checkout error (22)`가 발생했다. 라이선스 서버를 조사한 결과 발급된 Arnold feature가 **`88169ARNOL_2026_0F` 하나뿐**이었다.

```
lmutil lmstat -a -c 27000@localhost
→ 88169ARNOL_2026_0F  (3000석, 만료 2027-06-25)
```

2025용 feature가 없으므로 Maya 2025 제출은 구조적으로 불가능했다. Maya 2026으로 통일하자 라이선스는 통과했으나, 렌더는 같은 지점에서 다시 중단됐다.

**② 색 관리 환경변수 — 실제 원인**

```
ERROR | [color_manager_ocio] could not read
        '<MAYA_RESOURCES>/OCIO-configs/Maya-legacy/config.ocio' OCIO profile.
```

`<MAYA_RESOURCES>`는 **Maya 내부에서만 치환되는 토큰**이다. Deadline은 이 문자열을 그대로 OS 환경변수 `OCIO`에 넣고, Arnold는 존재하지 않는 경로를 읽으려다 렌더를 중단했다.

Maya의 Color Management를 꺼도 해결되지 않았다. 색 관리를 끄면 Arnold가 자체 기본 관리자(`ai_default_color_manager_ocio`)로 넘어가는데, 그것 역시 같은 환경변수를 읽기 때문이다. **씬 설정으로는 우회할 수 없는 문제**였다.

**③ 주입 지점 특정**

```
\\223.194.101.83\deadline_repo\plugins\MayaBatch\MayaBatch.py  (322행)

elif ocioConfig:
    self.SetEnvironmentAndLogInfo("OCIO", RepositoryUtils.CheckPathMapping( ocioConfig ))
```

`ocioConfig`는 Maya 제출기가 보낸 값이다. 따라서 Deadline Monitor의 Job Environment로 덮어쓰려는 시도는 실패했다 — 플러그인이 렌더 직전 다시 설정하기 때문이다.

### 2-3. 적용한 해결책

```python
elif ocioConfig:
    _ocio = RepositoryUtils.CheckPathMapping( ocioConfig ).replace(
        "<MAYA_RESOURCES>", "C:/Program Files/Autodesk/Maya2026/resources")
    if not os.path.isfile( _ocio ):
        _ocio = "C:/Program Files/Autodesk/Maya2026/resources/OCIO-configs/Maya-legacy/config.ocio"
    self.SetEnvironmentAndLogInfo("OCIO", _ocio)
```

토큰을 치환하고, 치환된 경로가 Worker에 실제로 존재하지 않으면 기본 설정으로 되돌린다.

**폴백이 필요했던 이유**는 외부 씬 테스트에서 드러났다. 실습실 작업 PC는 Maya 2025이고, 일부 설치본은 OCIO 설정 폴더 자체가 누락되어 있다. 이 경우 토큰이 아닌 **실제 경로 문자열**이 그대로 전달되므로 치환만으로는 막을 수 없다.

## 3. 발견한 운영 리스크

### 3-1. 플러그인 수정은 신규 Job으로만 검증된다

Worker는 Repository의 플러그인을 **Job ID별 폴더에 복사해 캐시**한다.

```
C:\ProgramData\Thinkbox\Deadline10\workers\<Worker명>\plugins\<JobID>\MayaBatch.py
```

같은 Job을 Requeue하면 Job ID가 유지되므로 캐시된 이전 버전이 실행된다. 플러그인을 수정한 뒤에는 반드시 새 Job으로 제출해야 한다. 이번 디버깅에서 수정이 반영되지 않는 것으로 오판할 뻔한 지점이었다.

### 3-2. GPU 렌더링은 결과를 비결정적으로 만든다

외부 씬 테스트에서 3프레임 중 1프레임만 실패했다. Job 상태는 `Completed`였다.

```
M211-05 : GPU 9420MB available  →  렌더 성공
M211-07 : GPU  373MB available  →  [gpu] no GPU matching requirements found
                                   → Failed batch render
```

Arnold는 VRAM이 부족해도 CPU로 폴백하지 않고 렌더를 중단한다. **동일한 작업이 Worker의 GPU 점유 상태에 따라 갈리는 것**이다.

240프레임 중 일부만 누락되는 형태로 나타나므로 발견이 늦다. 공용 팜에서는 Render Device를 CPU로 고정하는 것이 타당하다고 판단해 매뉴얼에 반영했다.

### 3-3. 외부 파일 반입 시 참조가 전부 유실된다

졸준위에게 받은 테스트 샷(39MB)을 분석한 결과다.

| 항목 | 수량 | 경로 |
| --- | --- | --- |
| 텍스처 | 42개 | `D:/Projects/OVER/Prod/texture/...` |
| 레퍼런스 | 1개 | `D:/Projects/.../g80_Rigging_master.ma` |

씬 파일에는 파일 자체가 아니라 경로만 기록된다. 문제는 **이 상태로도 렌더가 중단되지 않는다**는 점이다. 텍스처 없이, 캐릭터가 빠진 채로 완료된다.

대책으로 마야의 `File → Archive Scene`(참조 파일 일괄 패키징) 사용을 매뉴얼과 학생 안내문에 명시했다.

## 6. 남은 과제

이번 주로 시스템 검증은 끝났다. 남은 것은 **학생이 실제로 쓰게 만드는 일**이다.

| 항목 | 내용 | 비고 |
| --- | --- | --- |
| 문서 배포 | 갱신된 매뉴얼·안내문을 NAS에 적용 | 완료된 파일 적용만 남음 |
| 학번 등록 | 예약 시트 사용자 명단 입력 | 졸준위 협조 |
| 폴더 생성 | 학번별 input·output 폴더 사전 생성 | 명단 확보 후 |
| 시범 운영 | 학생 1~2명 대상 실제 렌더 진행 | 문제 발생 시 즉시 대응 |
| Worker 점검 | M211-07 GPU·메모리 점유 프로세스 확인 | 부분 실패 재발 방지 |

### 운영 중 주시할 지점

측정이 아니라 **문제가 생겼을 때 어디를 볼지**를 미리 정해둔 항목이다.

**텍스처 읽기 지연** — Worker 20대가 같은 NAS에서 텍스처를 읽으므로, 4K 텍스처가 많은 씬에서는 렌더보다 파일 전송에 시간이 더 걸릴 수 있다. 렌더가 유난히 느리면 Task 로그의 `scene creation time` 비중을 먼저 본다. 이 값이 전체의 대부분을 차지하면 연산이 아니라 I/O 문제다. 실제로 느려지는 경우에만 `.tx` 변환(타일·밉맵 구조)을 검토한다.

**결과물 수량 확인** — Job이 `Completed`여도 실패한 프레임이 있을 수 있다. 학생에게도 결과물 장수를 세어보도록 안내문에 명시했다.

## 8. 논문 반영 사항

이번 주 확인한 내용 중 논문에 기록할 지점은 다음과 같다.

**상용 미들웨어의 통합 비용**
Deadline은 완성된 제품이지만 DCC 버전 조합에 따라 플러그인 스크립트 수정이 불가피한 지점이 존재한다. 도입 비용을 산정할 때 고려되어야 할 항목이다.

**실패가 드러나지 않는 구조**
Job 상태 표시(`Completed`)와 실제 성공 여부가 일치하지 않는 경우가 반복적으로 관찰됐다. 운영자가 결과물 수량으로 교차 검증해야 하며, 이는 모니터링 설계의 요구사항이 된다.

**이기종 환경의 비결정성**
동일한 작업이 Worker의 상태(VRAM 점유)에 따라 다른 결과를 내는 사례를 관측했다. 재현성을 확보하려면 렌더 디바이스를 팜 정책으로 고정해야 한다는 근거가 된다.

세 가지 모두 교내 실습실이라는 조건 — 관리 권한 제한, 소프트웨어 버전 혼재, 공용 사용 — 에서 비롯된 문제다. 상용 솔루션을 그대로 적용할 수 없는 환경에서 어떤 보정이 필요했는지를 기록으로 남긴다.
