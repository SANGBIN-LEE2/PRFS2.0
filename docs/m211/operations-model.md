# M211 렌더팜 운영 모델 — 타임블럭 · 그룹 · 라이선스

학생이 렌더팜을 **어떻게 나눠 쓰는가**에 대한 설계. PRFS 1.0(2025, 강세영)의 운영 체계를 분석해 승계하고, 프로젝트 분량 기준 차등 배정을 추가했다.

---

## 1. 왜 나누는가

렌더팜은 한 대의 장비가 아니라 **실습실 PC 전체**다. 선착순 자유 사용으로 두면 한 팀이 마감 주간 내내 점유하고 나머지는 아무것도 못 한다. 그래서 두 축으로 나눈다.

| 축 | 단위 | 역할 |
| --- | --- | --- |
| 시간 | 타임블럭 | 언제 쓸지 |
| 장비 | 그룹(Pool) | 어느 PC를 쓸지 |

---

## 2. 타임블럭

```
타임블럭 1개 = 4시간
```

| | 사용 가능 시간 | 하루 블럭 |
| --- | --- | --- |
| 평일 (월~금) | `19:00 ~ 11:00` | 4개 |
| 주말 (토·일) | 24시간 | 6개 |

평일 낮 `11:00~19:00` 은 수업이 있어 제외한다. 실습실 PC를 수업에서 써야 하기 때문이다.

---

## 3. 그룹 (Pool)

Worker PC를 **4개 레인**으로 분할한다. 한 타임블럭에 **네 팀이 서로 방해 없이 동시에** 렌더할 수 있다.

Deadline에서는 Pool로 구현한다. Worker의 Pool 목록은 **우선순위 순서**를 가지므로, 자기 레인을 1순위에 두고 나머지 레인을 뒤에 붙이면 **자기 팀 몫은 보장되면서 유휴 장비가 생기지 않는다.**

### 적용된 배정 (2026-10-21)

```
M211-00         none                                     ← 라이선스 서버, 제외
M211-01 ~ 04    pool_a, pool_b, pool_c, pool_d, none
M211-05 ~ 09    pool_b, pool_c, pool_d, pool_a, none
M211-10 ~ 14    pool_c, pool_d, pool_a, pool_b, none
M211-15 ~ 19    pool_d, pool_a, pool_b, pool_c, none
```

| 레인 | PC | 대수 |
| --- | --- | --- |
| `pool_a` | 01, 02, 03, 04 | 4 |
| `pool_b` | 05, 06, 07, 08, 09 | 5 |
| `pool_c` | 10, 11, 12, 13, 14 | 5 |
| `pool_d` | 15, 16, 17, 18, 19 | 5 |

**순서를 한 칸씩 돌려놓는다.** 네 레인 모두 2순위를 `pool_a`로 두면 다른 레인이 쉴 때 남는 PC가 한쪽으로 몰린다. 돌려놓으면 고르게 퍼진다.

### 동작

| 상황 | 결과 |
| --- | --- |
| 네 팀 동시 | 각자 예약한 레인 PC를 먼저 받는다 |
| 한 팀만 | **19대 전부 그 팀 작업에 투입된다** |
| 두 팀 | 각자 레인 확보 후 남는 PC를 나눠 가진다 |

지연은 길어야 **프레임 한 장**이다. 다른 레인 프레임을 이미 렌더 중인 PC는 그것을 끝내고 넘어온다 (`Frames Per Task = 1`).

학생 쪽 절차는 바뀌지 않는다 — 제출 시 예약한 레인을 `Pool`에 지정하는 것 그대로다.

### 설정 방법

```
Deadline Monitor → Tools → Manage Pools
→ Workers 목록에서 해당 레인 PC 다중 선택
→ Pool Operations → Clear      (기존 배정 전부 비움)
→ 왼쪽 Pools 에서 하나씩 클릭 → Add    (넣은 순서 = 우선순위)
```

`Add`는 목록 맨 뒤에 붙는다. 풀을 여러 개 동시에 선택하고 Add하면 순서가 보장되지 않으므로 **하나씩** 넣는다. `Assigned Pools` 열의 쉼표 순서가 곧 우선순위다.

> M211-00은 라이선스 서버이므로 어느 레인에도 넣지 않는다.


## 5. 라이선스 — 주당 예약 상한

"라이선스"는 **주당 예약할 수 있는 블럭 수**를 뜻하는 운영 단위다. 소프트웨어 라이선스와는 무관하며, 학생 안내 시 이 구분을 명확히 해야 한다.

```
라이선스 1개 = 주 8블럭 = 32시간
```

### 분량 기준 차등 배정

렌더 시간은 영상 길이에 거의 비례한다. 6분짜리와 2분짜리에게 같은 시간을 주면 6분짜리는 마감 안에 끝내지 못한다.

| 프로젝트 분량 | 라이선스 | 주 타임블럭 | 주 사용시간 |
| --- | --- | --- | --- |
| 3분 이하 | 1 | 8 | 32시간 |
| 3분 초과 ~ 6분 이하 | 2 | 16 | 64시간 |
| 6분 초과 | 3 | 24 | 96시간 |

**라이선스 합계가 16을 넘으면 공급 128블럭을 초과**한다. 그때는 구간을 조정한다. 산정식은 신청 시트 `01_신청서` 탭 F열 한 줄이다.

```
=IF(E5<=3, 1, IF(E5<=6, 2, 3))
```

### 상한이지 할당이 아니다

전체 신청자의 상한 합계가 공급량을 넘어도 운영은 가능하다. 라이선스는 **"여기까지 예약할 수 있다"** 는 뜻이고 블록은 선착순이기 때문이다.

PRFS 1.0 실측 (2025):

```
9팀 · 라이선스 합계 13 · 상한 합계 104블럭  ≤  공급 128블럭
```

## 6. 신청 수집 항목

```
팀 프로젝트명
팀장 학번
팀장 이메일
프로젝트 분량 (분)   ← 최종 상영 길이 기준
```

졸업준비위원회가 접수하고 시트에 입력한다. 라이선스·타임블럭·사용시간은 자동 산정된다.

## 7. 운영 규칙

| 규칙 | 근거 |
| --- | --- |
| 예약 시간 외 Worker PC 로그인 금지 | 예약한 팀이 그룹 전체를 온전히 써야 함 |
| 제출 시 예약한 그룹과 동일하게 지정 | 다른 그룹을 고르면 타 팀 작업과 충돌 |
| 미등록 학번 자동 삭제 | 신청하지 않은 사용 차단 |
| 쓰지 않을 블록은 미리 반납 | 선점 후 방치가 가장 큰 낭비 |
| 결과물 수령 후 NAS 폴더 비우기 | EXR 시퀀스가 볼륨을 채우면 팜 전체가 멈춤 |

### 위반 시

| 적발 횟수 | 처리 |
| --- | --- |
| 1회 | 경고 및 기록 공유 |
| 2회 | 해당 주 라이선스 −2블럭 |
| 3회 | 3일간 사용 정지 |
| 4회 이상 | 팀 사용권 박탈 (졸준위·지도교수 협의) |

---

## 8. 심야 블록 활용

렌더는 사람이 지켜보지 않아도 돌아간다. `23:00-03:00` 과 `03:00-07:00` 이 가장 한가하므로 **저녁에 제출하고 자는 방식**을 권장한다.

이걸 모르는 학생이 많아 저녁 시간대에만 몰리는 현상이 반복된다. 공지에 명시해야 한다.
